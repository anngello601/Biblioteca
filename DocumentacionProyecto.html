Resumen

NovaBook es una aplicación web para consultar y administrar un catálogo de libros. Los visitantes pueden explorar el catálogo; los usuarios registrados pueden gestionar su perfil y carrito; y los administradores pueden administrar libros y usuarios. La aplicación separa la interfaz Angular de una API REST Spring Boot y guarda la información persistente en PostgreSQL alojado en Supabase.

Problema abordado

La administración de un catálogo y de las interacciones de compra requiere centralizar libros, usuarios, inventario y navegación en una interfaz accesible.

Solución implementada

Frontend Angular, API REST en Java/Spring Boot, persistencia JPA/Hibernate y servicios de catálogo bibliográfico externo.

Tecnologías

Java 25, Spring Boot 4.1.1, Angular 22, TypeScript 6, PostgreSQL, Supabase, JWT y jsPDF.

Resultado y límite

El catálogo y los flujos principales están implementados. El pago Visa/BCP y el comprobante actual son demostrativos: no existe procesamiento bancario ni emisión tributaria.

Capítulo I. Planteamiento del proyecto

1.1 Realidad problemática

Una biblioteca o librería necesita mantener un catálogo consultable y actualizado, controlar datos de libros, atender a sus usuarios y ofrecer una experiencia digital consistente. Si estas tareas se realizan mediante procesos separados, puede ser más difícil encontrar libros, mantener el inventario y administrar las cuentas.

1.2 Formulación del problema

Problema general: ¿Cómo desarrollar un sistema web integrado que facilite la consulta y administración de un catálogo de libros, usuarios y carrito de compras?

Problemas específicos: ¿Cómo exponer las funciones mediante servicios REST? ¿Cómo persistir libros y usuarios? ¿Cómo autenticar usuarios y limitar funciones administrativas? ¿Cómo integrar Angular con el backend y servicios externos de libros?

1.3 Objetivos

  • Objetivo general: desarrollar una aplicación web de biblioteca con Angular y Spring Boot.
  • Implementar operaciones REST para libros, cuentas, administración y carrito.
  • Persistir entidades con JPA/Hibernate en PostgreSQL.
  • Autenticar mediante JWT y distinguir los roles ADMIN y CLIENTE.
  • Integrar búsquedas bibliográficas con Google Books y Open Library.
  • Desplegar frontend y backend en servicios de nube configurados por el proyecto.

1.4 Justificación

Tecnológica

Separa presentación, lógica de negocio y persistencia, y usa interfaces REST para conectar el frontend y el backend.

Operativa

Concentra en una aplicación la consulta de libros, la gestión administrativa, el perfil de usuario y el carrito.

Económica

La solución usa frameworks y servicios con planes de entrada, pero algunos servicios externos pueden requerir cuotas o facturación según uso.

1.5 Alcance

  • Catálogo de libros, búsqueda, filtros, paginación y consulta de libros más vendidos.
  • Registro, inicio de sesión, perfil y carga de avatar.
  • Administración de libros y usuarios para cuentas con rol administrador.
  • Carrito por usuario y un flujo de pago exclusivamente de demostración.
  • Generación local de un PDF marcado sin validez tributaria.

1.6 Limitaciones identificadas en el código

  • El carrito se guarda en memoria del proceso; se pierde al reiniciar el backend y no se comparte entre varias instancias.
  • El pago no se conecta con Visa, BCP ni otra pasarela; los datos de tarjeta de prueba no se envían al backend.
  • El flujo de pago simulado calcula datos para la vista/PDF, pero no persiste una venta, no descuenta stock y no crea una boleta legal.
  • La dirección se escribe manualmente y se incluye en el PDF generado en el navegador.
  • Se requiere configurar y rotar las credenciales de servicios externos mediante variables de entorno antes de publicar.

Capítulo II. Marco teórico

2.1 Desarrollo web y arquitectura cliente-servidor

El cliente Angular presenta las páginas y envía solicitudes HTTP. El servidor Spring Boot valida esas solicitudes, aplica reglas de negocio y consulta o actualiza la base de datos. La respuesta vuelve normalmente como JSON.

2.2 Spring Boot y arquitectura del backend

Spring Boot configura la aplicación Java y sus componentes. La inyección de dependencias conecta controladores, servicios y repositorios. Los controladores reciben solicitudes REST; los servicios concentran operaciones de negocio; los repositorios acceden a las entidades persistentes.

2.3 API REST y métodos HTTP

  • GET: consultar libros, usuarios o contenido del carrito.
  • POST: registrar usuarios, iniciar sesión, agregar libros al carrito o simular el pago.
  • PUT: modificar libros o el perfil de usuario.
  • DELETE: quitar artículos, vaciar el carrito o eliminar registros administrativos.

Los controladores devuelven códigos HTTP y respuestas JSON. El frontend consume la API con HttpClient de Angular.

2.4 Pruebas

El proyecto incluye pruebas Java con JUnit/Spring Boot. La guía adjunta propone TDD, Postman y Swagger; no se encontró evidencia suficiente para afirmar que se haya seguido TDD ni que exista una colección Postman. Springdoc aparece como dependencia del backend; la disponibilidad de su interfaz debe verificarse en el entorno desplegado.

2.5 Persistencia

JPA define el mapeo entre entidades Java y tablas. Hibernate implementa la persistencia ORM. El backend usa PostgreSQL mediante JDBC y Spring Data repositories. Las operaciones de libro y usuario se guardan en la base de datos; el carrito, en cambio, es temporal y vive en memoria.

2.6 Seguridad web

Las contraseñas se codifican con BCrypt. Al iniciar sesión, el backend firma un JWT con una vigencia de dos horas; el frontend lo envía como Authorization: Bearer …. El backend recupera el usuario asociado y algunos controladores verifican el rol ADMIN.

Precaución: las propiedades de configuración incluyen valores predeterminados que parecen credenciales. No se reproducen aquí. Deben rotarse y mantenerse solo en variables de entorno o en un gestor de secretos.

3.1.2 Requerimientos no funcionales

  • Seguridad: contraseñas BCrypt, JWT y control de rol en endpoints administrativos.
  • Disponibilidad: depende del backend, PostgreSQL/Supabase y servicios externos.
  • Rendimiento: catálogo paginado; las consultas externas se ejecutan desde backend y dependen de la latencia de terceros.
  • Escalabilidad: el carrito en memoria limita el escalado horizontal hasta que se persista en una base compartida o caché distribuida.

3.2 Casos de uso principales

  1. Visitante: navegar el catálogo, filtrar libros y ver detalles.
  2. Cliente: registrarse, iniciar sesión, editar perfil, añadir libros al carrito y revisar el checkout de prueba.
  3. Administrador: gestionar libros y usuarios; importar metadatos de un catálogo externo al formulario de libro.

3.3 Modelo de negocio

El cliente consulta libros y puede organizar una selección en su carrito. El administrador mantiene el catálogo. En la versión actual el checkout solo ensaya la experiencia de pago; no produce una transacción comercial.

3.4 Modelo de clases y 3.5 Modelo relacional

Usuario

Nombre, correo, contraseña codificada, avatar y rol.

Libro

Nombre, tipo, editorial, año, precio, stock, portada, autor y descripción.

Boleta y detalle

Las entidades modelan usuario, fecha, total y líneas de libros. El servicio BoletaService puede guardar una venta real en base de datos, pero el endpoint actual de checkout de prueba no lo invoca.

Carrito

Mapa temporal de usuario → libro → cantidad, mantenido en memoria por CarritoService.

Relaciones persistentes del modelo: un usuario puede estar asociado a varias boletas; una boleta contiene varios detalles; cada detalle referencia un libro.

4.3 Seguridad y roles

Los roles que aparecen en la lógica del proyecto son ADMIN y CLIENTE. El registro público fuerza el rol de cliente; los endpoints de administración comprueban que el usuario autenticado sea administrador. El cierre de sesión elimina el token del cliente; el endpoint backend de logout no mantiene una lista de revocación.

4.4 Frontend Angular

La aplicación organiza la interfaz por páginas/componentes y usa rutas protegidas para el carrito, checkout, perfil y administración. Los servicios Angular encapsulan peticiones HTTP. El token de sesión se guarda en sessionStorage. El campo de dirección del checkout es de escritura manual.

4.5 Integración frontend-backend

En desarrollo el frontend apunta a http://localhost:8080/api; en producción consume la API en https://biblioteca-backend-3nz3.onrender.com (rutas bajo /api). El frontend está publicado en https://biblioteca-f7gp.onrender.com. Para solicitudes protegidas, un interceptor del frontend adjunta el token JWT. CORS permite el origen local y el dominio frontend configurado en el backend.

Flujo de búsqueda del catálogo externo

  1. El formulario de administración llama a GET /api/libros/catalogo/buscar?q=….
  2. El backend busca primero en Google Books.
  3. Si la búsqueda primaria falla o queda vacía, intenta Open Library.
  4. El frontend permite copiar los metadatos al formulario; el administrador revisa y guarda el libro localmente.

Flujo del checkout de prueba

  1. El usuario escribe una dirección y completa únicamente los datos ficticios indicados en el formulario.
  2. La validación de tarjeta ocurre en el navegador; esos campos no forman parte de la solicitud al backend.
  3. El endpoint protegido verifica usuario, carrito y stock, calcula total y devuelve un DTO marcado DEMO_NO_REAL.
  4. La pantalla de resultado ofrece el PDF local, claramente marcado como demostración y sin validez tributaria.

Capítulo VI. Despliegue

6.1 Preparación y configuración

El backend usa Maven Wrapper; la configuración Docker declara una etapa de compilación con Maven/Temurin 25 y una etapa de ejecución Temurin 25 JRE. Las URLs de API, base de datos, almacenamiento, clave JWT y Google Books se configuran mediante propiedades de Spring.

6.2–6.5 Servidor y publicación

El frontend está publicado en https://biblioteca-f7gp.onrender.com y apunta al backend publicado en https://biblioteca-backend-3nz3.onrender.com (API bajo /api). El backend configura CORS para localhost y este origen frontend. La base de datos y el bucket de avatares están configurados para Supabase. Estas son configuraciones del proyecto; este documento no certifica que los servicios remotos estén activos o disponibles.

6.6 Cloud y Docker

Docker empaqueta el backend como aplicación Java ejecutable. El frontend se construye de forma independiente con Angular. Para reproducir el despliegue hay que definir las variables de entorno en la plataforma y mantener las claves fuera del repositorio.

Acción necesaria antes de publicar: eliminar los valores secretos predeterminados del archivo application.properties, rotar credenciales ya expuestas y configurar variables del entorno en el proveedor de despliegue. No compartir copias de configuración que incluyan claves.

Conclusiones

  1. La aplicación integra una interfaz Angular con una API REST implementada en Spring Boot.
  2. JPA/Hibernate y PostgreSQL cubren la persistencia de libros y usuarios, mientras el carrito continúa siendo temporal en memoria.
  3. JWT y BCrypt forman parte del flujo de autenticación; los roles observados son ADMIN y CLIENTE.
  4. Google Books y Open Library amplían la búsqueda bibliográfica y reducen la dependencia de una única fuente externa.
  5. El pago Visa/BCP y el PDF son demostrativos; no se debe presentar el flujo como una transacción o comprobante legal.
  6. La compilación y pruebas de backend verificadas son satisfactorias, aunque las pruebas Angular de AppComponent requieren configuración adicional.

Recomendaciones

  1. Rotar cualquier credencial expuesta y usar únicamente variables de entorno o un gestor de secretos.
  2. Persistir el carrito en una base de datos o caché compartida para evitar pérdida al reiniciar y permitir varias instancias.
  3. Si se requiere vender, contratar e integrar un checkout alojado/tokenizado de un proveedor autorizado; nunca enviar CVV o tarjeta al backend propio.
  4. Para emitir boletas válidas, integrar un proveedor autorizado de comprobantes electrónicos y usar datos tributarios reales verificados.
  5. Agregar pruebas unitarias para el carrito, validaciones de stock, permisos administrativos y checkout simulado.
  6. Configurar router/proveedores en las pruebas Angular y documentar una colección de pruebas REST reproducible.
  7. Verificar cuotas, límites, disponibilidad y atribución exigida por Google Books, Open Library y Supabase.
